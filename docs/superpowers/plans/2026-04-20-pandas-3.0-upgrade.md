# pandas 2.3.3 → 3.0.x Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the workspace from `pandas==2.3.3` to the latest `pandas 3.0.x`, absorb Copy-on-Write and PyArrow-backed-string-dtype semantics, end with zero pandas `DeprecationWarning` / `FutureWarning` across backend + lfx unit suites.

**Architecture:** Three phases — (1) CoW pre-flush on 2.3 via conftest opt-in, (2) pin bump + override update + smoke probes for the three dep blockers, (3) full pandas-3 strict-warnings runtime loop. Each phase ends with one commit.

**Tech Stack:** uv (package manager), pytest (with strict `-W error::FutureWarning:pandas` flags), pandas 3.0.x, pyarrow 19.

**Spec:** `docs/superpowers/specs/2026-04-20-pandas-3.0-upgrade-design.md`

## Global Ground Rules

Read these before starting any task.

- **Branch:** All work stays on `platform-multi-tenant`. No upstream push. No PRs to langflow-ai/langflow (per user policy).
- **Commit policy:** User requires explicit permission before every `git commit`. Every commit task in this plan says "pause and ask user to commit" — follow that literally. If the user declines, stash the change or leave it uncommitted but continue the next task. Never commit silently.
- **lfx tests:** Require `LFX_TEST_ALLOW_LANGFLOW=1` when run from the repo-level venv.
- **Baseline drift:** The 2.3 upgrade report (`docs/superpowers/specs/2026-04-20-pandas-2.3-upgrade-report.md`) documents known pre-existing failures. Any delta *beyond* that list at Phase 3 exit is pandas-3-induced and must be addressed. That file is the reference — do not re-discover the baseline from scratch.
- **Strict pandas flags:** These four flags are used throughout. Collectively called `PANDAS_STRICT` in the plan:
  ```
  -W error::DeprecationWarning:pandas
  -W error::FutureWarning:pandas
  -W error::DeprecationWarning:pandas.*
  -W error::FutureWarning:pandas.*
  ```
- **Third-party un-stricting:** If a non-pandas library emits a pandas warning inside its own call stack, un-strict only that module via `-W "default::<warning>:<module>"` and record the exception in the final report. Do not patch upstream packages.
- **Abort condition:** If `uv lock` fails for a pandas cap not listed in the spec (a fourth blocker), or if Phase 1 uncovers more than ~5 chained-mutation breakage sites, **stop and report** — do not grind through.

## Task 5: Fix CoW chained-mutation breakage

**Files:** Determined by Task 4 triage. Every file you change here is a file our code owns (not in `.venv`).

**Decision rule for each break site:** pandas 3.0 guidance is to rewrite chained mutations as explicit assignment. Do **not** add `.copy()` unless the original code clearly relied on view semantics. Prefer `df.loc[...] = value` or `df = df.assign(col=value)` over `.copy()`.

- [x] **Step 1: For each break site, write/extend a test that exercises the exact mutation**

(Skip this step if the failing inner-loop test already exercises the exact path — just re-run it after the fix.)

- [x] **Step 2: Rewrite the chained mutation**

Concrete patterns and rewrites:

```python
# BAD: chained mutation (CoW silent no-op)
df[df["col"] > 0]["col"] = 1

# GOOD: explicit loc assignment
df.loc[df["col"] > 0, "col"] = 1
```

```python
# BAD: mutation through view returned by method chain
df.reset_index(drop=True).rename(columns={"a": "b"}, inplace=True)

# GOOD: capture the result as a new assignment
df = df.reset_index(drop=True).rename(columns={"a": "b"})
```

```python
# BAD: mutation after slicing with a boolean mask
sub = df[df["x"] > 0]
sub["y"] = sub["x"] * 2   # CoW: no longer propagates to df

# GOOD: explicit .copy() only when the intent was a separate frame
sub = df[df["x"] > 0].copy()
sub["y"] = sub["x"] * 2

# OR: write back via .loc on the original frame
df.loc[df["x"] > 0, "y"] = df.loc[df["x"] > 0, "x"] * 2
```

- [x] **Step 3: Re-run the inner loop from Task 4 Step 1 + Step 2**

Must be clean of pandas-emitted warnings in our code. Repeat Step 2 for remaining breaks. If the fix list exceeds ~5 files, stop and report (per global ground rules — "too big" is a signal).

**Files:**

Create the file with:

```python
"""Smoke probe: ibm-watsonx-ai under pandas 3.0 override.

ibm-watsonx-ai declares `pandas<2.4.0` but we force `pandas>=3.0` via
tool.uv.override-dependencies. This probe asserts the import graph and
first-call pandas surface survive the resolver lie.

No network, no auth — if the dep needs credentials to run its pandas
code path, we fall back to attribute-existence assertions.
"""
import pytest

pytest.importorskip("ibm_watsonx_ai")


@pytest.mark.smoke
def test_ibm_watsonx_ai_imports_cleanly():
    import ibm_watsonx_ai
    import ibm_watsonx_ai.foundation_models.utils  # touches pandas-adjacent internals

    assert ibm_watsonx_ai.__version__


@pytest.mark.smoke
def test_ibm_watsonx_ai_api_client_instantiates():
    """APIClient construction exercises pandas-backed internals without a network call."""
    from ibm_watsonx_ai import APIClient

    # APIClient accepts a credentials dict; passing empty/dummy triggers validation-only
    # paths. If the import graph is broken on pandas 3, we'll crash here with
    # ImportError / AttributeError / TypeError rather than a credential/auth error.
    with pytest.raises(Exception) as exc_info:  # noqa: PT011 — we want any failure here
        APIClient(credentials={"url": "https://example.invalid"})
    # Auth/credential errors are fine (that's the expected failure mode).
    # ImportError / AttributeError / TypeError means the override is a lie.
    msg = str(exc_info.value)
    forbidden = ("ImportError", "has no attribute", "NoneType")
    for bad in forbidden:
        assert bad not in type(exc_info.value).__name__ + msg, (
            f"watsonx broke at construction on pandas 3: {bad} in {msg!r}"
        )
```

## Task 18: Phase 3 fix loop

**Files:** Determined by Task 17 triage. Specific patterns below.

- [x] **Step 1: Fix PyArrow-string-dtype assertions (category A)**

Canonical patterns:

```python
# BAD: assumes object dtype
assert df["col"].dtype == "object"

# GOOD: accept both pyarrow-backed string and numpy object (covers CI + downgrade scenarios)
assert str(df["col"].dtype) in ("object", "string", "str")
```

```python
# BAD: direct comparison against python string literal 'object'
if df["col"].dtype == object:
    ...

# GOOD: use pandas API
if pd.api.types.is_object_dtype(df["col"]) or pd.api.types.is_string_dtype(df["col"]):
    ...
```

- [x] **Step 2: Fix NaN equality shifts (category B)**

```python
# BAD: relies on np.nan identity
assert row["x"] is np.nan
assert row["x"] == np.nan  # always False anyway, but PyArrow strings surface pd.NA

# GOOD: use pd.isna
assert pd.isna(row["x"])
```

- [x] **Step 3: Fix removed-API call sites (category C)**

Match 2.3-era audit patterns from the 2.3 spec:

```python
# BAD: df.append removed in pandas 2.0 but may still sit in cold paths
df = df.append(row_dict, ignore_index=True)

# GOOD:
df = pd.concat([df, pd.DataFrame([row_dict])], ignore_index=True)
```

```python
# BAD: DataFrame.applymap / Series.applymap (removed in 3.0)
df = df.applymap(func)
s = s.applymap(func)

# GOOD:
df = df.map(func)
s = s.map(func)
```

```python
# BAD: errors='ignore' in pandas I/O conversions (removed in 3.0)
x = pd.to_numeric(raw, errors="ignore")

# GOOD: explicit try/except (pandas recommendation)
try:
    x = pd.to_numeric(raw, errors="raise")
except (ValueError, TypeError):
    x = raw  # or whatever the pre-3.0 behavior relied on
```
